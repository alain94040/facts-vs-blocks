# Experiment G: tracing one impressive answer, and whether it is built from copies of small templates

An independent experiment on an existing open model. It runs forward passes, patches activations
and builds attribution graphs with pretrained transcoders. It trains nothing.

**Why.** Experiments C, D and E looked for building blocks at the level of whole layers of Qwen and
found none: no layer reuses another layer's operation. This experiment starts from the other end.
It takes one answer that looks clever, finds the parts of the model that actually produce it, and
then asks whether those parts are **copies of a few small templates**: many parts that do the same
job, wired the same way, each with a different "setting" (which variable, which number).

The clever answer is **running a short program in the head**, with no written steps:

```
a = 4
b = a + 3
x = 9
a = b - 5
print(a)
```

The model must answer `2`. To do so it has to keep several variables, ignore `x`, notice that `a`
was overwritten, look up the latest value of each variable, and do arithmetic, all inside one
forward pass. (A program whose last line combines two computed variables is beyond one pass for
these models; see the PROG section.)

**What "building block" means here, and what it does not.** A part is an attention head or a
transcoder feature (one sparse direction that a layer reads and writes). Two pictures are tested:

- **Reuse:** one part serves many uses. The feature for "the value held by a variable" is the same
  whichever variable it is.
- **Copies:** many parts do the same job for different settings. There is one feature for "the
  value held by `a`", another for "held by `b`", and so on, and each copy is wired to the next
  stage the same way. This is the picture in which the model is built from many similar instances
  of a small template, possibly spanning several layers.

A single feature is already a tiny template ("detect a pattern, write a direction") repeated tens
of thousands of times; that is true of every model and is not what is tested. A **template** here
is a group of at least four features that do the same job for different settings *and* connect to
the next stage in a pattern that follows the setting. Program tracing suits this test because
every program makes the model do the same jobs several times, each time with a different variable
or number.

The experiment cannot count every template in the model; it counts those that program tracing
uses. With 8 variable letters and 10 digits, a family has at most 8, 10 or 80 members. Shared or
selective features may also be generic parts (for example "this token is a number"); the nulls
below exist to separate the two.

## 2. Tasks

Every task is generated by `circuit/tasks.py` from a seed. Every item has a prompt, a gold answer,
and its difficulty settings. Each prompt starts with three worked examples of the same family and
level, separated by a blank line, then the test item. The examples use different numbers and
names from the test item.

**Answer tokens.** Qwen tokenizers split numbers into single digits. So for every family the gold
answer is **one token**: a digit 0–9 for number answers, and for names a name whose first token is
the whole name (check this in the tokenizer and drop any name that is not one token, with a
leading space). Accuracy is: the gold token is the top next-token prediction after the prompt.

### PROG: program tracing

Variables from `a b c d e x y z`. Values are integers 0–9 when written. A line is one of:
- a literal assignment `v = L`;
- a copy `v = u`;
- an operation with a literal `v = u op L`, with `op` from `+ - *`.

A line never combines two variables. The answer's computation contains at most **two** operations.
The program is a list of lines, then `print(v)`; the prompt then ends with `\n# output: ` and the
answer is the next token.

**Why these limits.** Probes 1 and 2 (`results/circuit/probe/`, `results/circuit/probe2/`) showed
the boundary on Qwen3-4B. It was 0.95–1.00 accurate on copies with two overwrites and two
distractors, and 0.98 on two operations with an overwrite. It fell to 0.44 on the original
three-step program, whose last line combines two computed variables. That program was solved 1.00
when the model could write its steps. The task stays on the side the model solves in one pass.

Levels (each level adds one thing):

| Level | Lines before print | Operations on the answer's path | Copies on the path | Overwrites | Distractor lines |
| --- | --- | --- | --- | --- | --- |
| P1 | 2 | 1 | 0 | 0 | 0 |
| P2 | 3 | 2 | 0 | 1 | 0 |
| P3 | 4 | 2 | 0 | 1 | 1 |
| P4 | 6 | 2 | 1 | 1 | 1 |
| P5 | 7 | 2 | 1 | 2 | 2 |

Generate by rejection. Keep a program only if:
- every intermediate value is 0–20 and the printed value is 0–9;
- from P2, at least one line of the answer's computation reads an overwritten variable;
- the printed value is not equal to any literal in the program, and not equal to the value of any
  other variable at the end, so copying a number from the prompt cannot score.

### STORY: the same programs, told as a story

Each PROG item has a twin in which every variable is a person and every value a count of one
object kind: `Ann has 4 marbles. Bob has 3 more marbles than Ann. Cal has 9 marbles. Then Ann
gives away marbles until she has 5 fewer than Bob.` … `How many marbles does Ann have?` The computation and the
answer are identical to the twin. Write one sentence template per operation and use it for every
item; the templates go in `circuit/tasks.py` and do not change after Task 1.

### ORDER: transitive ordering

`N` people, each pair adjacent in height given once, in shuffled order (`Dan is taller than Eve.`
…), then `Who is the shortest?` or `Who is the tallest?` or `Who is second tallest?` with answer
` Name`. Levels O1–O4: N = 3, 4, 5, 6.

### TWOHOP: two-hop questions

Use the official-language relation and the country list of Experiment E (`middle/countries.py`,
read-only): `The official language of the country whose capital is Lima is`. Keep only items whose
answer is one token with a leading space. There is one level, H1.

### Controls for later tasks

- ARITH: the arithmetic of PROG with no variables (`(4 + 3) * 2 - (4 + 3) =`), answer one digit.
- TEXT: 200 chunks of 128 tokens from the validation split of `wikitext-103-raw-v1`.

## 3. Tasks

### Circuit task 0: set-up and a check that the tools run on the Mac

1. Create `circuit/.venv`, install `circuit-tracer` (latest release) and pin everything.
2. Load the development model and its transcoders with `circuit_tracer.ReplacementModel` on MPS.
   If MPS fails, try CPU and record it.
3. Checks on 20 PROG P1 prompts, written to `results/circuit/task0/metrics.json`:
   - logits of the circuit-tracer model match plain `transformers` logits in the same dtype: max
     absolute difference of the final-position log-probabilities ≤ 0.05;
   - build one attribution graph per prompt with the **graph settings** below; record wall time
     per graph, peak memory, and the library's replacement and completeness scores.
4. Repeat 2 and 3 with the main model on 5 prompts.

**Graph settings (revision 3).** These apply to every attribution graph in this experiment:
- float32 for the model and the transcoders. bfloat16 rounding alone moves the answer's
  log-probability by 0.3–0.8 in plain `transformers`;
- the library's lazy-encoder loading for the main model;
- `safetensors` 0.7.0 and the device wrapper `circuit/ct_compat.py`, both inside `circuit/`;
- `batch_size = 64`. It changes only speed and memory, not the graph;
- `max_feature_nodes = 4096` (revision 4; revision 3 tried 8192 first). The library attributes features in order of their estimated
  influence on the answer and stops at the cap. Without the cap, the first main-model prompt kept
  all 90,241 active features, needing about 34 GB for one internal matrix and about an hour per
  graph. Default pruning (node threshold 0.8) already drops the low-influence features, so the cap
  should change pruned graphs little. Step 5 measured it on the development model at 8192: median
  node overlap 0.88 with the uncapped graphs, completeness 0.816 vs 0.819.

5. **Effect of the cap.** On the development model, rebuild the 20 graphs of step 3 with
   `max_feature_nodes = 8192` and compare with the uncapped graphs already built. Report:
   - median completeness and replacement score, with and without the cap;
   - the Jaccard overlap of the pruned graphs' feature sets, per prompt, and its median.

   These numbers are reported, not gated. Gate G2 still applies to every graph in Task 4.

**Memory handling (revision 4).** The revision 3 rerun ran close to the 20-minute limit but
peaked at 85–91 GB. Two things that do not change any graph caused most of it: 37 GB of
process memory left over from loading, and about 45 GB of cached, unused GPU memory. So:
- after building the `ReplacementModel`, delete every loading-time object, run `gc.collect()`
  and `torch.mps.empty_cache()`, and record the process memory (RSS);
- call `gc.collect()` and `torch.mps.empty_cache()` after every graph;
- the agent may change *how* the model is loaded and freed (for example loading once, saving the
  converted weights under `data/cache/circuit/`, and reloading them in a fresh process). It may
  not change any graph setting.

**Same-graph check.** With the memory handling in place, rebuild the 5 main-model graphs at
`max_feature_nodes = 4096`. They must match the revision 3 graphs: identical node sets, and
completeness and replacement scores within 1e-4. If they do not match, write `STOP.md`.

**Gate G0.** On the main model with the graph settings and `max_feature_nodes = 4096`:
logits match as above, one graph takes ≤ 20 minutes, and either
- peak memory ≤ 48 GB, or
- if it is still above 48 GB, swap grows by at most 25 GB during the 5 graphs and the Mac
  stays responsive. Swapping costs time, which the 20-minute limit already measures.

Record peak memory, RSS after loading, the allocator's cached memory and swap growth. If G0 fails,
write `STOP.md` with the numbers. Do not try other models or other graph settings.

### Circuit task 2: minimal pairs

From here on, work only on the main model, at each family's chosen level. Fresh items, seeds
1001–1400: the first 200 are DEV (used to choose anything that must be chosen), the last 200 are
TEST (used once, for reported numbers). Keep only items the model answers correctly.

For each PROG item build four corrupted twins, each identical in token count:

| Corruption | What changes | Answer |
| --- | --- | --- |
| `on-path` | one literal used by the answer's computation | changes (reject if it does not) |
| `off-path` | one literal in a distractor line | same |
| `overwrite` | the value of the overwriting line, so that the old value of the variable would now give a different answer than the new one | changes |
| `rename` | all variable names replaced by other letters | same |

The patching score for a clean/corrupt pair with different answers is the logit difference
`LD = logit(clean answer) − logit(corrupt answer)`. Report the fraction of pairs where both clean
and corrupt are answered correctly; keep only those pairs.

### Circuit task 3: where the information sits (activation patching)

On TEST pairs of type `on-path` and `overwrite` (100 each):

1. **Residual stream, layer × position.** Run the corrupt prompt and patch in the clean residual
   stream at one (layer, token position); record the fraction of `LD` restored:
   `(LD_patched − LD_corrupt) / (LD_clean − LD_corrupt)`. Positions are grouped by role (the
   literal that changed, the variable name on that line, later lines that read it, the `print`
   line, the final position) so items of different length can be averaged.
2. **Heads at the final position.** Patch each head's output at the final position alone; record
   the same fraction. List the 20 heads with the largest mean restoration.
3. **MLPs.** Same, for each layer's MLP output at the final position and at the `print` variable.
4. **Control:** the same patches on `off-path` and `rename` pairs must restore nothing because
   nothing changes; report the mean absolute change in the clean logit as the noise level.

5. **Lookup heads.** On 200 TEST items, for every head, the mean attention from the final position
   to the literal token of the **latest** assignment of the printed variable, and to the literal of
   its **earlier** assignment when there is one. A **lookup head** has mean attention ≥ 0.3 to the
   latest literal and at most half that to the earlier one. Report the number of lookup heads,
   their layers, and their Task 3.2 restoration. Several lookup heads are copies at the level of
   heads.

Output heat maps, `results/circuit/task3/heads.csv` and `results/circuit/task3/lookup_heads.csv`.

### Circuit task 4: attribution graphs

1. Build an attribution graph for each of 40 TEST items (PROG at the chosen level), with the
   library defaults for pruning. Save the graph files under `data/cache/circuit/graphs/` and their
   summaries (nodes, edges, replacement and completeness scores) in `results/circuit/task4/`.

**Gate G2.** Median completeness ≥ 0.7 over the 40 graphs. If it fails, write `STOP.md`; the
patching results of Task 3 stand on their own.

2. **Core features.** A feature node is identified by (layer, feature index). The PROG **core set**
   is every feature that appears in the pruned graph of at least 50% of the 40 items, at any
   position. Record its size and its layers.
3. **Is the core set needed?** On 200 TEST items, zero the core set's activations (with the
   library's intervention function, at all positions) and measure accuracy. Compare with zeroing
   a **matched random set**: the same number of features, from the same layers, each chosen to
   have activation frequency on TEXT within ×2 of the core feature it replaces. 20 random sets.
   Report core accuracy, the random sets' mean and 5th–95th percentile.
4. Also report the accuracy after zeroing the core set restricted to each third of the layers.

### Circuit task 5: copies or one shared part (PROG)

**Data.** FACT: 600 fresh PROG items at the chosen level (seeds 2001–2600) that the model answers
correctly. Run each once and record every transcoder feature's activation at every layer, at four
**roles**:

| Role | Position | Labels |
| --- | --- | --- |
| VAR-W | the variable name on an assignment line | its letter; the value it is assigned |
| LIT | a literal | its digit |
| VAR-R | a variable name read on the right-hand side | its letter; the value it holds at that point |
| FINAL | the last position | the printed letter; the answer |

Values are known from the program. Values above 9 are labelled "10+" (one extra class).

A feature is **active** for a role at a layer if it is non-zero on at least 5% of that role's
positions. Drop **generic** features (non-zero on more than 5% of TEXT positions) from everything
in this task, and report how many were dropped per layer.

**5.1 Classify every active feature.** For a label with `k` classes, the **share** of a feature is
`max_c m(c) / Σ_c m(c)`, where `m(c)` is its mean activation on positions with class `c`. A share
is **significant** if it is above the 99.9th percentile of 1,000 shares with the labels shuffled
across positions. Classify each active feature, in this order:

1. **conjunction**: on the letter × value table, share ≥ 0.5 and significant;
2. **letter-selective**: letter share ≥ 0.5 and significant;
3. **value-selective**: value share ≥ 0.5 and significant;
4. **shared**: otherwise.

Its **preferred class** is the class (or cell) with the largest `m`. Report counts per layer, role
and type in `results/circuit/task5/classes.csv`.

**5.2 Families.** For each (layer, role, type) with at least 4 distinct preferred classes among its
selective features, those features form one **family**; its **coverage** is the number of distinct
preferred classes (at most 8 letters, 11 values or 88 cells). Report every family with its size and
coverage. If more than 40 families exist, keep the 40 with the largest summed node influence in the
Task 4 PROG graphs for steps 5.3–5.5 and say so.

**5.3 Same wiring, following the setting?** For two families X (layer `l`) and Y (layer `l'`,
`l < l' ≤ l + 4`) with the same type of label (letters or values), the **connection matrix**
`M[c, c']` is the mean virtual weight from members of X preferring `c` to members of Y preferring
`c'`. Virtual weights use the transcoder encoder of the target and decoder of the source, through
two paths, reported separately:
- **direct**: `w = enc_Y · dec_X` (residual stream only);
- **through a head**: `w = enc_Y · W_OV(h) · dec_X` for every head `h` in layers `l+1 … l'`; keep the
  head with the largest score below, and compute its null the same way (maximum over heads).

The **diagonal score** is the mean of `M` on matching classes minus the mean off them, divided by
the standard deviation of `M`. Its null is 1,000 shuffles of Y's preferred classes. A family pair is
**wired by setting** if its score is above the null's 99th percentile. Report every pair tested, the
number that pass, and the number expected by chance (1% of pairs tested).

**5.4 A common part?** For each family, the **template fraction** `T = |mean of unit decoder
vectors|²`. It is 1 if all members write the same direction and near 0 if they are unrelated.
Compare with 1,000 sets of the same size drawn from active non-generic features of the same layer,
matched in TEXT frequency within ×2. For value families, also fit the top 6 principal components
of the members' decoder vectors with `cos(2πv/P)` and `sin(2πv/P)` for `P` = 2, 5, 10 (Kantamneni
and Tegmark 2025); report R² and its 99th percentile under 1,000 label shuffles.

**5.5 Does the setting do what it says?** For each of the 3 letter-selective VAR-W families with
the largest node influence, on 100 TEST items: at the variable name of one on-path assignment line
(variable `v`), set the activations of members preferring `v` to 0 and set those preferring another
letter `u` used in the program to their mean active value in FACT. The **predicted answer** is the
program's output with `v` renamed `u` on that line only; keep items where it differs from the
original and is 0–9. Report the fraction of items whose top answer becomes the predicted one, and
the same for 20 swaps of matched random features (same counts, same layers, TEXT frequency within
×2).

**5.6 In the actual graphs.** In the 40 PROG graphs of Task 4: the share of total node influence
carried by family members; and, over edges between members of two families, the share whose source
and target have the same preferred class, against 1,000 shuffles of preferred classes.

Output `results/circuit/task5/` (`classes.csv`, `families.csv`, `wiring.csv`, `template.csv`,
`swap.csv`, `graphs.json`) and one plot per family pair that passes 5.3 showing `M`.

## 4. Budget
