# Experiment G: tracing one impressive answer, and which of its parts are reused

An independent experiment on an existing open model. It runs forward passes, patches activations
and builds attribution graphs with pretrained transcoders. It trains nothing.

**Why.** Experiments C, D and E looked for building blocks at the level of whole layers of Qwen and
found none: no layer reuses another layer's operation. This experiment starts from the other end.
It takes one answer that looks clever, finds the parts of the model that actually produce it, and
then asks which of those parts also produce answers to *other, different-looking* tasks.

The clever answer is **running a short program in the head**, with no written steps:

```
a = 4
b = a + 3
a = b * 2
c = a - b
print(c)
```

The model must answer `7`. To do so it has to keep several variables, notice that `a` was
overwritten, look up the latest value of each variable, and do arithmetic, all inside one forward
pass.

**What "building block" means here, and what it does not.** A part is an attention head or a
transcoder feature (one sparse direction that a layer reads and writes). A part is a **block** for
this experiment if it is needed for program tracing *and* is needed for at least one task that
looks different on the surface (the same problem told as a story, ordering people by height, a
two-hop question), more than a frequency-matched random part is. The experiment cannot produce a
complete list of the model's blocks, and a part that is shared is not proof of a general
"reasoning module": it may be a generic part (for example "this token is a number") that every
task touches. The nulls below exist to separate the two.

The rules in `CLAUDE.md` apply. In addition:

| Role | Model | Transcoders |
| --- | --- | --- |
| Main | `Qwen/Qwen3-4B` (36 layers) | `mwhanna/qwen3-4b-transcoders` |
| Development | `Qwen/Qwen3-0.6B` | `mwhanna/qwen3-0.6b-transcoders-lowl0` |
| Comparison (Task 1 only) | `Qwen/Qwen2.5-7B-Instruct`, as in Experiments C to E | none |

Use the exact model the transcoder repository's config names (base or instruct) and record its
name and revision in `metrics.json`. Use plain text prompts with no chat template and no thinking
mode. Layers are numbered from 0.

## 2. Tasks

Every task is generated by `circuit/tasks.py` from a seed. Every item has a prompt, a gold answer,
and its difficulty settings. Each prompt starts with three worked examples of the same family and
level, separated by a blank line, then the test item. The examples use different numbers and
names from the test item.

**Answer tokens.** Qwen tokenizers split numbers into single digits. So for every family the gold
answer is **one token**: a digit 0–9 for number answers, and for names a name whose first token is
the whole name (check this in the tokenizer and drop any name that is not one token, with a
leading space). Accuracy is: the gold token is the top next-token prediction after the prompt.

### PROG: program tracing

Variables from `a b c d e x y z`. Values are integers 0–9 when written. Operations: `+`, `-`, `*`
by a literal or another variable. The program is a list of assignment lines, then `print(v)`,
then the prompt ends with `\n# output: ` and the answer is the next token.

Levels (each level adds one thing):

| Level | Lines before print | Overwrites (a variable assigned twice) | Distractor lines (never used by the answer) |
| --- | --- | --- | --- |
| P1 | 3 | 0 | 0 |
| P2 | 4 | 1 | 0 |
| P3 | 5 | 1 | 1 |
| P4 | 6 | 2 | 1 |
| P5 | 7 | 2 | 2 |

Generate by rejection: keep a program only if every intermediate value is 0–20 and the printed
value is 0–9; at least one line of the answer's computation reads an overwritten variable (from
P2); the printed value is not equal to any literal in the program and not equal to the value of
any other variable at the end (so copying a number from the prompt cannot score).

### STORY: the same programs, told as a story

Each PROG item has a twin in which every variable is a person and every value a count of one
object kind: `Ann has 4 marbles. Bob has 3 more marbles than Ann. Then Ann gives away marbles until
she has twice as many as Bob has.` … `How many marbles does Cal have?` The computation and the
answer are identical to the twin. Write one sentence template per operation and use it for every
item; the templates go in `circuit/tasks.py` and do not change after Task 1.

### ORDER: transitive ordering

`N` people, each pair adjacent in height given once, in shuffled order (`Dan is taller than Eve.`
…), then `Who is the shortest?` or `Who is the tallest?` or `Who is second tallest?` with answer
` Name`. Levels O1–O4: N = 3, 4, 5, 6.

### TWOHOP: two-hop questions

Use the official-language relation and the country list of Experiment E (`middle/countries.py`,
read-only): `The official language of the country whose capital is Lima is`. Keep only items whose
answer is one token with a leading space. There is one level, H1.

### Controls for later tasks

- ARITH: the arithmetic of PROG with no variables (`(4 + 3) * 2 - (4 + 3) =`), answer one digit.
- TEXT: 200 chunks of 128 tokens from the validation split of `wikitext-103-raw-v1`.

## 3. Tasks

### Circuit task 0: set-up and a check that the tools run on the Mac

1. Create `circuit/.venv`, install `circuit-tracer` (latest release) and pin everything.
2. Load the development model and its transcoders with `circuit_tracer.ReplacementModel` on MPS.
   If MPS fails, try CPU and record it.
3. Checks on 20 PROG P1 prompts, written to `results/circuit/task0/metrics.json`:
   - logits of the circuit-tracer model match plain `transformers` logits: max absolute
     difference of the final-position log-probabilities ≤ 0.05;
   - build one attribution graph per prompt with the library's default settings; record wall time
     per graph, peak memory, and the library's replacement and completeness scores.
4. Repeat 2 and 3 with the main model on 5 prompts.

**Gate G0.** On the main model: logits match as above, one graph takes ≤ 20 minutes, and peak
memory ≤ 48 GB. If the full transcoder set does not fit, use the library's offload or lazy-loading
option and record which. If G0 fails, write `STOP.md` with the numbers. Do not try other models.

### Circuit task 1: screening (review stop at the end)

Generate 300 items per family per level (seeds 1–300; these items are SCREEN and are not used
again). For each of the three models, record accuracy per family and level, and the mean
log-probability of the gold token.

Also score two shortcut baselines on PROG, without a model: "answer = last digit in the prompt"
and "answer = most frequent digit in the prompt". By construction these should be near 0; report
them anyway.

**Choosing the level.** For each family, the **chosen level** on the main model is the highest level
with accuracy ≥ 0.85, provided the next lower level is also ≥ 0.85. A family with no such level is
dropped and listed in the report.

**Gate G1.** PROG has a chosen level of P2 or higher. If not, the main task becomes the next family
in the order ORDER, TWOHOP that has a chosen level, every PROG step below is run on that family
instead, and the report says so in its first line. If none qualifies, write `STOP.md`.

Output `results/circuit/task1/accuracy.csv` (model, family, level, n, accuracy, mean log-prob) and
one plot. Stop for review.

### Circuit task 2: minimal pairs

From here on, work only on the main model, at each family's chosen level. Fresh items, seeds
1001–1400: the first 200 are DEV (used to choose anything that must be chosen), the last 200 are
TEST (used once, for reported numbers). Keep only items the model answers correctly.

For each PROG item build four corrupted twins, each identical in token count:

| Corruption | What changes | Answer |
| --- | --- | --- |
| `on-path` | one literal used by the answer's computation | changes (reject if it does not) |
| `off-path` | one literal in a distractor line | same |
| `overwrite` | the value of the overwriting line, so that the old value of the variable would now give a different answer than the new one | changes |
| `rename` | all variable names replaced by other letters | same |

The patching score for a clean/corrupt pair with different answers is the logit difference
`LD = logit(clean answer) − logit(corrupt answer)`. Report the fraction of pairs where both clean
and corrupt are answered correctly; keep only those pairs.

### Circuit task 3: where the information sits (activation patching)

On TEST pairs of type `on-path` and `overwrite` (100 each):

1. **Residual stream, layer × position.** Run the corrupt prompt and patch in the clean residual
   stream at one (layer, token position); record the fraction of `LD` restored:
   `(LD_patched − LD_corrupt) / (LD_clean − LD_corrupt)`. Positions are grouped by role (the
   literal that changed, the variable name on that line, later lines that read it, the `print`
   line, the final position) so items of different length can be averaged.
2. **Heads at the final position.** Patch each head's output at the final position alone; record
   the same fraction. List the 20 heads with the largest mean restoration.
3. **MLPs.** Same, for each layer's MLP output at the final position and at the `print` variable.
4. **Control:** the same patches on `off-path` and `rename` pairs must restore nothing because
   nothing changes; report the mean absolute change in the clean logit as the noise level.

Output heat maps and `results/circuit/task3/heads.csv`.

### Circuit task 4: attribution graphs

1. Build an attribution graph for each of 40 TEST items (PROG at the chosen level), with the
   library defaults for pruning. Save the graph files under `data/cache/circuit/graphs/` and their
   summaries (nodes, edges, replacement and completeness scores) in `results/circuit/task4/`.

**Gate G2.** Median completeness ≥ 0.7 over the 40 graphs. If it fails, write `STOP.md`; the
patching results of Task 3 stand on their own.

2. **Core features.** A feature node is identified by (layer, feature index). The PROG **core set**
   is every feature that appears in the pruned graph of at least 50% of the 40 items, at any
   position. Record its size and its layers.
3. **Is the core set needed?** On 200 TEST items, zero the core set's activations (with the
   library's intervention function, at all positions) and measure accuracy. Compare with zeroing
   a **matched random set**: the same number of features, from the same layers, each chosen to
   have activation frequency on TEXT within ×2 of the core feature it replaces. 20 random sets.
   Report core accuracy, the random sets' mean and 5th–95th percentile.
4. Also report the accuracy after zeroing the core set restricted to each third of the layers.

### Circuit task 5: reuse across tasks

1. Repeat Task 4 steps 1–2 for STORY, ORDER, TWOHOP and ARITH (40 items each, chosen level), giving
   one core set per family. Skip any family dropped in Task 1.
2. **Overlap.** For each family `T`, the overlap `|core(PROG) ∩ core(T)| / |core(PROG)|`, and the
   same overlap for 1,000 random sets drawn like the matched random sets of Task 4.3. Report the
   overlap, the null mean and its 95th percentile.
3. **Causal reuse.** Zero core(PROG) and measure accuracy on 200 TEST items of every other family,
   and on TEXT (mean next-token loss). Compare with the 20 matched random sets. Then zero
   core(PROG) ∩ core(T) and core(PROG) \ core(T) separately and measure both PROG and T.
4. **Generic parts.** A feature is **generic** if it is active (non-zero) on more than 5% of TEXT
   positions. Report every overlap number twice: with all features and with generic features
   removed.

Output `results/circuit/task5/overlap.csv` and `results/circuit/task5/ablation.csv`.

### Circuit task 6: what the shared parts look like

For each feature in core(PROG) ∩ core(STORY) after removing generic features (if more than 30,
take the 30 with the largest summed attribution in the PROG graphs):

- its 20 top-activating TEXT positions with 10 tokens of context each;
- its mean activation per token role in PROG (literal, variable name on assignment, variable name
  on read, operator, `print` line, final position) and in STORY (number, person name on first
  mention, person name on later mention, final position);
- its top 5 output tokens through the unembedding.

Write these to `results/circuit/task6/features.md` as plain tables. Do not label the features:
the labels are for the human review.

### Circuit task 7: report (review stop)

`results/circuit/REPORT.md` with every number above, the plots, and this decision table. Report
which rows hold; do not interpret beyond them.

| Result | What it means |
| --- | --- |
| Task 4.3: zeroing core(PROG) drops accuracy below the random sets' 5th percentile | The graph found parts the answer needs |
| Task 5.2: overlap with STORY above the null's 95th percentile, after removing generic features | Code and story share specific parts: candidate blocks |
| Task 5.3: zeroing core(PROG) hurts STORY (or ORDER, TWOHOP) beyond random, but leaves TEXT within 0.05 nats of random | The shared parts are task-relevant, not general text machinery |
| Overlap with ARITH is as large as with STORY | What is shared may be the arithmetic, not the variable tracking |
| Overlap above null only before removing generic features | What is shared is generic: no evidence for blocks |
| No overlap above null for any family | Each task has its own parts at this resolution: a negative result |
| Task 3: restoration for `overwrite` pairs concentrated in a few heads at the final position (top 5 heads ≥ 50% of the best single-layer residual restoration) | Looking up the latest value of a variable is done by a few heads |

## 4. Budget

About 2–4 hours on the Mac, most of it in attribution graphs (40 graphs × 5 families plus Task 0).
If Task 0 shows one graph takes more than 5 minutes, reduce every "40 items" above to 20 before
starting Task 4, and say so in the report. That change is decided by Task 0 timing only, never by
results.
